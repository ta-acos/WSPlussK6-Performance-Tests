1. What This Project Does (In Simple Words)

This project pretends to be real users of the WebSak Plus system. It signs in, creates cases, creates journal posts, attaches documents, and measures how fast and reliable the system is under different levels of activity (light, normal, heavy, spikes, long‑running).

Business Goal

Confirm the system can handle expected and peak workloads without slowing down too much or producing errors.

How It Works

Automated virtual users call the real APIs in controlled patterns (scenarios). All results are turned into an easy‑to‑read HTML report.

Core Outcomes

  • Response time (speed)
  • Error rate (reliability)
  • Stability under load
  • Pass or fail vs. agreed targets

2. Quick Start – If You Only Want To Run a Test

  1. Open a terminal in the project folder.
  2. Run a simple quick health test: npm run simple
  3. Run a normal load test: npm run load
  4. When it finishes, open the HTML report inside src/reports/

You do not need to edit any files for basic usage.

3. What Happens When I Run a Test Command?

Example command: npm run load (which internally runs a k6 command with environment variables).

1. You start the command
The chosen script in package.json invokes the k6 test file (for example a script in tests/api/...) and sets scenario type (e.g. load_test).
2. Initialization Phase
Before any virtual users run actions, configuration files are read:
  • environments.json – which server to target (host, protocol).
  • autotest.json – defines load patterns (how many users, how long).
  • performance-thresholds.json – target performance limits.
  • websak-api-config.json and users-config.json – endpoints and test accounts.
3. Options & Scenarios Built
config-manager.js combines scenario settings and thresholds → passes them to k6 so it knows how many virtual users, duration, and pass/fail criteria.
4. Virtual Users Start
Each simulated user picks a test account (from users-config.json), authenticates via auth-module.js, and begins performing actions (create case, etc.).
5. Workflows Run
test-workflow.js and modules like case-module.js, jp-module.js, payload-module.js assemble realistic API requests.
6. Measurements Collected
For every API call the time taken and success/failure are recorded (metrics like http_req_duration, http_req_failed).
7. Threshold Check
At the end k6 compares actual performance to targets (for example “95% of requests must be faster than 4.5 seconds”). Any breach = FAIL status for that rule.
8. Report Generated
report-generator.js builds an HTML report (plus a JSON summary). You open it from src/reports/.

5. Reading the HTML Report

The HTML report is your main artifact. Key areas:

  • Executive Summary – One‑screen verdict (PASS/FAIL notes).
  • KPI Cards – Success rate, error rate, key percentiles (95% / 99%).
  • Latency Distribution – Shows spread; watch 95th percentile value.
  • Threshold Table – Each rule and whether it passed.
  • Verbose Logs (optional) – Only if you ran a :verbose script.
Color meanings:
Green = on target. Yellow = keep an eye on it. Red = needs investigation.
Why 95th percentile? It tells you how slow the slowest typical users are (excluding rare outliers). If this is high, many users feel slowness.

6. Frequently Asked Questions

How do I know if the test PASSED?

If all thresholds in the “Threshold Table” show PASS. Any FAIL means the test overall should be treated as failed.

Why are some tests called smoke / load / stress / spike / endurance?

They mimic different real‑world patterns: quick check, normal traffic, pushing limits, sudden bursts, and long stability check.

Can I ignore red iteration_duration?

Iteration duration measures a whole loop of user actions—not just one API call. It can appear larger and is explained inline in the report.

Where can I adjust performance targets?

Only in src/config/performance-thresholds.json. Edit carefully then run npm run validate:perf.

How do I switch environment (e.g. dev vs autotest)?

Add -e CONFIG_ENV=dev to the k6 command or use a script that sets it.

How do I add more virtual users?

Update the scenario definition (e.g. in autotest.json) or temporarily override via environment variables in a custom script.

7. Glossary (Plain Language)

  • Virtual User (VU) – A simulated user performing actions.
  • Scenario – Pattern describing how many users and how long.
  • Threshold – A performance rule (e.g., “95% of responses < 4.5s”).
  • Percentile (p95) – Value under which 95% of measurements fall.
  • Error Rate – Portion of API calls that failed.
  • Apdex – User satisfaction index (not heavily emphasized here but supported).
  • Bandwidth / Payload – Data being sent (e.g., document uploads).

8. What To Do After a Test

  1. Open the HTML report.
  2. Check for any red FAIL thresholds.
  3. If FAIL: capture the report, note scenario + environment, raise to engineering with the JSON summary.
  4. If all PASS but yellow areas growing: schedule optimization discussion.
Never change thresholds to “green‑wash” a problem. Investigate root cause first (slow endpoint, document size, authentication slowness).

9. Safe Ways to Experiment

  • Run a smoke test first (fast, low risk).
  • Use :verbose variants only when debugging (they produce more output).
  • Change just one scenario parameter at a time when exploring.
  • Run npm run validate:perf before committing threshold changes.
